03 From Excel to timetable

From chaos to clarity.

Every term used to begin as three Excel workbooks: the rooms, the Modules and their Tutors, and the timetable itself. Keeping them in step meant checking rows against each other by hand, and a double-booked room could hide in plain sight.

  • Three spreadsheets to keep in step
  • Rooms, Modules and Tutors cross-checked by hand
  • Every change updated in several places
  • Clashes that are hard to spot by eye

One workspace. Six steps.

The same data, now in one place that checks it, shows it and keeps every change. Each step links to the feature that does it.

  1. 01ImportEvery row checked. Nothing is saved until you confirm.
  2. 02ValidateDouble-booked rooms and staff, rooms too small, staff unavailable.
  3. 03EditDrag, split and merge on screen, checked again as you go.
  4. 04Suggest fixesChanges that solve a problem without creating a new one.
  5. 05ReviewEvery save is a Version to compare or restore.
  6. 06ExportExcel that imports again, and print-ready A4 PDFs.

04 Features

Every step checked. Every change kept.

Six capabilities, each as problem, action and result, on real screens with fictional demonstration data. Select a picture to inspect it; pinch, double-tap or use the zoom button to see detail.

Conflict detectionValidate

Clashes surface on their own.

Problem
Across three workbooks, a room booked twice is easy to miss.
Action
Validate checks the term for double-booked rooms and staff, rooms too small for a session, and staff who are unavailable or not set up to teach a Module.
Result
Each finding names the room, the day, the weeks and both sessions, and the sessions carry a WARNING badge on the grid.

Not checked yet: students' clashes and teaching hours. Those rules wait on a decision from the client.

Coordinated fixesSuggest fixes

Fixes you can see before you choose.

Problem
Some clashes have no simple fix: moving one session alone creates a new clash.
Action
Suggest fixes searches for changes that solve a problem without creating a new one, including coordinated fixes that move several sessions together, and previews each one on the grid.
Result
Apply saves the fix as a new Version: here Version 3, with 0 findings, current and clean. History can undo it.

The searches suggest. People decide.

  • Preview. Drawn on the grid; nothing saved yet.
  • Apply. Version 3: 0 findings, current and clean.

Drag-and-drop editingEdit

Pick it up. Put it down.

Problem
In the workbooks, moving one session meant updating it in several places.
Action
Start editing, then drag the session to its new time. The editor follows the drop.
Result
Each move is checked again, with a warning if it creates a clash. Save Draft with a short note and the change becomes the next Version.
  • The editor follows. Start 15:00, end 17:00, not applied yet.

Split and mergeEdit

Reshape sessions, with the result shown first.

Problem
Sessions change shape: a 4-hour block becomes two, or two Streams of a Module are taught together.
Action
Split a 4-hour session into 2 × 2 h, or merge two Streams whose length, weeks, type and Tutor match.
Result
Both show the result before you apply it. The merge adds up the students and checks the room fits.

Version historyReview

Nothing is ever overwritten.

Problem
Save over a workbook and what it said before is gone.
Action
Every save is kept as a Version that can't be overwritten, with its note and exactly what changed.
Result
Compare any Version with the import, and restore an earlier one as a new Version.
  1. Version 1Imported from the term's workbook
  2. Version 2Room clash fixed: one session moves room
  3. Version 3Coordinated fix: two time changes, one room change

Excel and PDFImport · Export

From Excel, back to Excel.

Problem
The term arrives as Excel workbooks, and it has to leave as Excel and on paper.
Action
Import checks every row and shows what will change before anything is saved. Export the exact saved Version as a Change Review workbook or a clean Standard workbook, or print A4 PDFs by day or by Stage.
Result
The exported workbook imports again. Round trip at the feature freeze: export, re-import and compare found 0 missing, 0 added and 0 different.
  • Import, check. 99 rows, 0 errors, 0 warnings.
  • Import, confirm. Nothing saved until you say so.
  • Print. A4 landscape, by day or by Stage.

The workspace, four ways

The Day view gives each Stage a column; the Stage view follows one Stage through the week; the Week view puts Monday to Friday side by side; the Activity Inspector shows when, where and who for any session.

05 Engineering

Full-stack engineering, tested end to end.

A typed React client, a modular Spring Boot monolith and a versioned PostgreSQL schema, shipped through a pipeline that tests the whole stack in a real browser before anything is published.

AArchitecture BCI/CD CQuality

A

Full-stack architecture

Four layers, each with one job, running together in Docker Compose on Wintec's server.

  • Checked at every boundary

    Imports check every row before saving. The client checks the shape of every API response; contract tests hold the server to its OpenAPI specification.

  • Versioned by design

    Saves create Versions that can't be overwritten, and restoring one makes a new Version. The schema evolves only through numbered migrations.

B

Continuous integration and delivery

The real GitHub Actions workflow: every push to main is tested end to end, and only a fully green run publishes images.

  1. 1

    Code

    Pull request, then squash and merge into main. The critical set and the round trip run locally first; their results go in the pull request.

  2. 2

    Test

    • Backend unit and integration tests on a real PostgreSQL (Testcontainers)
    • Frontend Vitest, type check and production build
    • Five Playwright browser groups on throwaway Compose stacks
    • Infrastructure checks: deploy scripts, safety gates, Compose
  3. Gate: every check green

  4. 3

    Build

    Backend and frontend images, built natively on amd64 and arm64 runners.

  5. 4

    Registry

    Pushed to GitHub Container Registry as immutable images tagged with the commit; their digests are recorded.

  6. Gate: verified commit only

  7. 5

    Deploy Paused

    Checks the exact commit, pulls those images, backs up PostgreSQL with pg_dump and checks the backup, installs, then checks that the database, the app and the API are healthy.

Automatic deploys have been paused since 7 November 2026. CI still runs on every push to main, nothing is deployed, and the server keeps running the last deployed version.

  • Runs only from main
  • One deploy at a time
  • Backup before install
  • Health checks after
  • If CI fails, nothing deploys

06 Project background

A 2026 Wintec industry internship.

CFIT Timetable was built in 2026 by Zhida Chen and Khylle Mauricio as a Wintec industry internship project at the Centre for Information Technology. It took a real scheduling workflow from Excel workbooks to a full-stack, self-hosted application deployed on Wintec's server, with a user manual and a developer handover for whoever looks after it next.
