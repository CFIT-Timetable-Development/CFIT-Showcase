03 From Excel to timetable

From chaos to clarity.

Every term used to begin as three Excel workbooks: the rooms, the Modules and their Tutors, and the timetable itself. Keeping them in step meant checking rows against each other by hand, and a double-booked room could hide in plain sight.

  • Three spreadsheets to keep in step
  • Rooms, Modules and Tutors cross-checked by hand
  • Every change updated in several places
  • Clashes that are hard to spot by eye

One workspace. Six steps.

The same data, now in one place that checks it, shows it and keeps every change.

  1. Import
  2. Validate
  3. Edit
  4. Suggest fixes
  5. Review
  6. Export

  1. 01

    Import

    Bring in the term.

    Upload the rooms, the Modules and Tutors, and the term's timetable. Every row is read and checked, and you see what will change before you confirm. Nothing is saved until then.

  2. 02

    Validate

    See every problem at once.

    Validate lists double-booked rooms and staff, rooms that are too small, and staff who are unavailable or not set up to teach a Module. Each problem is also marked on the timetable itself.

  3. 03

    Edit

    Change it on screen.

    Drag a session to a new time, or edit its day, time and room. Split a long session or merge two Streams, with a preview first. Each change is checked again as you make it.

  4. 04

    Suggest fixes

    Let the search suggest.

    Ask for fixes and get changes that solve a problem without creating a new one, even when three sessions have to move together. You choose; nothing changes until you click Apply.

  5. 05

    Review

    Know exactly what changed.

    Every save becomes a Version. See what has changed since the import, compare it side by side, and restore any earlier Version if you need to.

  6. 06

    Export

    Send it out.

    Download a Change Review workbook to check, a clean Standard workbook that imports again, or print-ready A4 PDFs by day or by Stage.

04 Features

Every step checked. Every change kept.

Eight capabilities that turn a term's workbooks into a timetable people can trust. Each picture below is the real application, recorded with fictional demonstration data. Select a picture to enlarge it.

Excel import and validation

Start from the workbooks you already have.

The term arrives in the CFIT Standard Timetable template, with its Rooms and its Module & Tutor list. The import reads every row, reports errors and warnings, and shows what will happen before anything is saved.

  • Checks every row first
  • Shows what will change
  • Saves nothing until you confirm

Visual timetable workspace

One timetable, three ways to look at it.

The Day view gives each Stage its own column; the Stage view follows one Stage through the week; the Week view puts Monday to Friday side by side. Select any session and the Activity Inspector shows when and where it runs, who teaches it and the Module behind it.

CFIT Timetable · 2026 S2

Conflict detection

Clashes surface on their own.

Validate finds double-booked rooms and staff, rooms too small for a session, and staff who are unavailable or not set up to teach a Module. Each finding names the room, the day, the weeks and both sessions, and the sessions are flagged on the grid.

Not checked yet: students' clashes and teaching hours. Those rules wait on a decision from the client.

Suggest fixes

Fixes you can see before you choose.

Suggest fixes searches for changes that solve a problem without creating a new one. When no single move works, it finds coordinated fixes that move several sessions together, and previews each one on the grid. Applying a fix saves it as a new Version, so History can undo it.

The searches suggest. People decide.

Drag-and-drop editing

Pick it up. Put it down.

Start editing, then drag a session to its new time. The editor follows the drop, each move is checked again, and you are warned if it creates a clash. Save Draft with a short note and the change becomes the next Version.

A real recording, shown silently on a loop.

Split and merge

Reshape sessions, with the result shown first.

Split a 4-hour session into 2 × 2 h. Merge two Streams of a Module when their length, weeks, type and Tutor match: the dialog adds up the students and checks that the room fits. Both show the result before you apply it.

Version history

Nothing is ever overwritten.

Each save is kept as a Version that can't be overwritten. History lists every Version with its note and exactly what changed, and restores any Version of the term as a new one.

  1. Version 1Imported from the term's workbook
  2. Version 2Room clash fixed: one session moves room
  3. Version 3Coordinated fix: two time changes, one room change

Export and PDF printing

Ready for print. Ready for Excel.

Print A4 landscape PDFs by day or by Stage, made right in the browser. Export the exact saved Version as a Change Review workbook for checking, or as a clean Standard Timetable workbook that imports again.

05 Engineering and architecture

Full-stack engineering for real-world timetabling.

A modular Java monolith behind a typed React client, a versioned PostgreSQL schema, and a delivery pipeline that tests the whole stack in a real browser before anything ships.

The stack

Frontend
React 19 · TypeScript · Vite
Backend
Java 21 · Spring Boot 4.1 · JPA · Apache POI
Data
PostgreSQL 17 · Flyway (31 migrations)
Interfaces
REST API · OpenAPI contracts · contract tests
Delivery
Docker Compose · nginx · GitHub Actions · GHCR (amd64 + arm64)
Testing
JUnit · Testcontainers · Vitest · Playwright

From commit to verified release

  1. Pull requestBranch from main. Local unit, browser and critical-set results go in the pull request.
  2. Squash and mergeThe project owner reviews and merges into main.
  3. CI on GitHub ActionsBackend unit and integration tests, frontend tests, type check and build, five browser test groups and infrastructure checks. About 12 minutes.
  4. PublishOnly a green run publishes images for amd64 and arm64 to GHCR, tagged by commit.
  5. Deploy WintecBacks up the database with pg_dump and checks it, installs the new version, then runs health checks.

If CI fails, nothing deploys. Automatic deploys have been paused since 7 November 2026; the server keeps running the last deployed version.

  • Checked at every boundary

    Imports check every row before saving. The client checks the shape of every API response, and contract tests hold the server to its OpenAPI specification.

  • Versioned by design

    Saves create Versions that can't be overwritten; restoring one makes a new Version. The database schema evolves through numbered migrations.

  • Released with a safety net

    Every past real bug is a named browser path in the critical set. A deploy backs up the database before it installs anything.

  • Made to be handed over

    One package per feature, a twelve-chapter user manual, a developer handover and a log of every owner decision.
